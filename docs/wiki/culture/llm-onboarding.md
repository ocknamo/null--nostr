# LLM コントリビュータ向けオンボーディング

## Summary

ぬるぬるは LLM エージェントによる継続的な編集を前提とする (`AGENTS.md` 参照)。本ページは LLM (および LLM を扱う人間) に対し、ぬるぬるの**文化的判断軸**を最短で身につけてもらうための導入文書。

## 最初に読む順

1. `AGENTS.md` (運用ルール)
2. [[principles]] (五箇条)
3. [[not-doing]] (やらないことリスト)
4. [[../index|wiki index]] (該当領域への入口)
5. 該当領域のページ (例: timeline を触るなら [[../features/timeline]])

## 編集前チェック (LLM 用)

PR / 編集を提案する前に、内部で以下に答えを持つこと。

- [ ] この変更は五箇条のどれを支えているか?
- [ ] やらないことリストに抵触しないか?
- [ ] 影響プラットフォームは? (Web / Android / iOS / Rust / Wiki のいずれか)
- [ ] [[../ui/design-tokens|design tokens]] 外の値を追加しないか?
- [ ] 既存採用コピー ([[copy-style]]) を変更しないか?
- [ ] [[../decisions/README|ADR]] が必要な大きさの判断か?
- [ ] 変更内容に対応する Wiki ページがあるか? なければ追加が必要か?
- [ ] `docs/wiki/log.md` に追記すべき変更か?

## 出力規約

LLM が PR / Issue / Wiki ページを書くとき:

- **断定を避ける場面**: ソースコードで確認していない挙動は `Open Questions` 節に分離する。
- **コード変更**: ソースコードの該当ファイルを必ず引用する。
- **設計判断**: 五箇条のどれに該当するかを1行で書く。
- **言語**: 日本語を基本とする。コード識別子は英語のまま。
- **コミットメッセージ**: 1行目は日本語可だが、慣用的な英語 prefix (`feat:` `fix:` `docs:` 等) は使って良い。

## 良い PR / 悪い PR

### 良い PR

- 五箇条への言及がある。
- Before / After のスクリーンショットまたはログがある。
- 影響範囲が明示されている。
- 不確実な箇所が Open Questions として正直に書かれている。

### 悪い PR

- 「リファクタリング」のみで動機が書かれていない。
- 複数の関心事 (UI 改善 + ライブラリ更新 + コピー変更) が混ざっている。
- 「動くから」だけで送られている。
- 他の Nostr クライアントを根拠にしている (それ単独では不十分)。

## LLM への文化的注意

- ぬるぬるは **「NIP 数を増やすゲーム」をしない**。新しい NIP が出ても、それが日常体験に寄与しなければ実装しない。
- ぬるぬるは **「他クライアントに追いつくゲーム」をしない**。10年先を狙うので、現在の Nostr クライアント比較は判断材料の一部でしかない。
- ぬるぬるは **「派手な技術キーワードを表に出すゲーム」をしない**。Marmot / MLS / Lightning / ZK 等は基盤に隠す。

## Dwivedi 2023 への配慮

生成 AI は弱い文化を増幅する。LLM が無批判に PR を量産すれば、ぬるぬるの美意識は希釈される。本ページのチェックリストと Design Crit ([[design-crit]]) は、その希釈圧に対する制度的防壁である。
